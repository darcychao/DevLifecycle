# H5 Lifecycle Framework

AI-agent-driven software development lifecycle framework. Orchestrates specialized agents through a standardized PRD→SE→Story→Test→Dev→Code Review→Validation workflow with built-in challenge/audit and plugin extension mechanisms. Supports a Dev-Story shortcut path that bypasses upstream phases to focus on development coding.

## Architecture Overview

```
┌──────────────────────────────────────────────────────────────────┐
│                       CLAUDE.md (Orchestrator)                    │
├──────────────────────────────────────────────────────────────────┤
│  Agents Layer       │  SE Agent  │  Dev Agent  │  Test Agent     │
├──────────────────────────────────────────────────────────────────┤
│  Workflow Layer     │  Standard Lifecycle + Challenge + Plugin    │
│                     │  + Dev-Story Shortcut                       │
├──────────────────────────────────────────────────────────────────┤
│  Artifacts Layer    │  PRD │ SE Design │ Story │ Test Plan       │
├──────────────────────────────────────────────────────────────────┤
│  Standards Layer    │  Coding(JS/TS/Java/Python) │ Structure      │
├──────────────────────────────────────────────────────────────────┤
│  Plugin Layer       │  Custom hooks injected at each stage        │
└──────────────────────────────────────────────────────────────────┘
```

## Quick Start

### Phase 0: Framework Initialization (MANDATORY — first step for every project)

**Phase 0 is a hard prerequisite.** No lifecycle phase may execute before initialization completes. When a user invokes any lifecycle command, the orchestrator checks for `docs/.framework-init.lock`. If absent, the request is REJECTED and the user is directed to initialize first.

```
@CLAUDE.md 初始化框架
```

The orchestrator executes the 8-step protocol in §Phase 0 — scanning every file, detecting language/framework, identifying modules and dependencies, generating all foundational documentation, and writing the lock file. After completion, lifecycle operations proceed normally.

---

## Entry Points

### Entry A: Full Lifecycle (standard)
```
@CLAUDE.md 基于PRD开始开发流程
```
User provides a PRD. The framework executes the complete 7-phase lifecycle: PRD → SE Design → Story → Test Plan → Dev → Code Review → Validation.

### Entry B: Dev-Story Shortcut (accelerated)
```
@CLAUDE.md 基于Dev Story开始开发
```
User provides a pre-existing Dev Story document (`docs/dev-story.md`). The framework bypasses upstream design phases and focuses on development coding and downstream quality assurance.

**Shortcut entry detection:**
When the orchestrator detects `docs/dev-story.md` already exists (user-provided, not generated by the framework), it evaluates what additional artifacts are available:

| Artifacts Present | Entry Phase | Rationale |
|-------------------|-------------|-----------|
| Dev Story only | Phase 5 (Dev Coding) | No test plan exists; Dev Agent writes code, then Test Agent creates test plan and validates |
| Dev Story + Test Plan | Phase 5 (Dev Coding) | Test plan ready; Dev Agent codes against both story and test plan |
| Dev Story + Test Plan + Code already written | Phase 6 (Code Review) | User wants code reviewed against dev story |
| No dev story | Phase 1 (PRD) | Fall back to full lifecycle |

**Shortcut entry protocol:**
1. User provides Dev Story document and states intent (e.g., "基于这份dev story进行开发")
2. Orchestrator reads `docs/dev-story.md` and validates it against `framework/artifacts/dev-story.template.md`
3. Orchestrator checks for existing test plan, SE design, PRD
4. Orchestrator determines the appropriate entry phase and announces:
   ```
   检测到用户提供的Dev Story。当前可用的制品:
     - docs/dev-story.md ✓ (user-provided)
     - docs/test-plan.md ✗ (将自动生成)
     - docs/se-design.md ✗
     - docs/prd.md ✗
   入口阶段: Phase 5 (开发编码)
   流程: Phase 5 (Dev) → Phase 6 (Code Review) → Phase 7 (Validation)
   ```
5. For missing upstream artifacts, the framework generates minimal placeholder documents referencing the Dev Story as their source of truth
6. Proceed with the determined entry phase

**Shortcut constraints:**
- Without SE Design, the SE Agent's code review (Phase 6) uses the Dev Story as the primary design reference
- Without PRD, the Test Agent derives test cases directly from the Dev Story's implementation details
- The challenge mechanism still applies: any agent can challenge the Dev Story itself if it contains contradictions or impossibilities

## Phase 0: Initialization Protocol (8 Steps)

### Phase 0 Enforcement

The orchestrator MUST enforce the following rules:

1. **Pre-execution check:** Before ANY lifecycle operation (Entry A or Entry B), verify that the initialization marker exists at `docs/.framework-init.lock`. If absent, REJECT the request and respond:
   ```
   框架尚未初始化。请先执行:
     @CLAUDE.md 初始化框架
   ```

2. **Re-initialization:** If the user explicitly requests re-initialization (e.g., after major refactoring), delete the lock file and re-run Phase 0 from scratch.

3. **Incremental update:** If the project has changed significantly since the last initialization (the lock file is older than 30 days, or the user indicates structural changes), suggest re-initialization but do not force it.

4. **Empty project exemption:** If the project contains NO source files (genuinely empty or template-only), Phase 0 still executes but generates minimal scaffolding documents. The lock file is still created. This is documented in §Empty Project Handling below.

5. **Partial initialization is forbidden.** If any step of Phase 0 fails, the orchestrator MUST report the failure, roll back any partially generated docs, and instruct the user on how to resolve the issue before retrying.

### Step 0.1: Detect Language Stack & Project Metadata

**Objective:** Identify every programming language, framework, build system, and package manager used in the project.

#### 0.1.1 Build Manifest Detection

Scan the project root and all first-level subdirectories for build manifests. Order matters — check in this sequence:

| Priority | Manifest File(s) | Language | Framework Hints (look inside) |
|----------|-----------------|----------|------------------------------|
| 1 | `package.json` | JavaScript / TypeScript | `dependencies`: react/vue/angular→Frontend, express/koa/fastify→Backend, next/nuxt→Fullstack |
| 2 | `tsconfig.json` | TypeScript | Presence alongside package.json confirms TS |
| 3 | `pom.xml` | Java | `<parent>`: spring-boot-starter-parent→Spring Boot |
| 4 | `build.gradle` / `build.gradle.kts` | Java / Kotlin | `plugins`: org.springframework.boot→Spring Boot |
| 5 | `pyproject.toml` | Python | `[tool.poetry]`→Poetry, `[project]`→PEP 621 |
| 6 | `setup.py` / `setup.cfg` | Python | Legacy setuptools project |
| 7 | `requirements.txt` | Python | Plain pip dependencies |
| 8 | `Cargo.toml` | Rust | `[lib]`/`[bin]` sections |
| 9 | `go.mod` | Go | `module <path>` line |
| 10 | `*.csproj` / `*.sln` | C# | `<Project Sdk="...">` line |
| 11 | `Gemfile` | Ruby | Rails/Sinatra detection |
| 12 | `CMakeLists.txt` | C / C++ | Build configuration |
| 13 | `pubspec.yaml` | Dart / Flutter | Flutter SDK presence |

**Multi-root / monorepo detection:**
- If multiple first-level subdirectories each contain their own build manifest, flag as monorepo
- For monorepos, list each sub-project with its own language and framework
- The primary project is the one at the repository root; sub-projects are secondary

**No manifest found:**
- List all file extensions in the repository (`.py`, `.js`, `.ts`, `.java`, etc.)
- Present the top 3 detected extensions to the user and ask them to confirm the primary language
- Once confirmed, proceed; load or generate standards for that language

### Step 0.2: Comprehensive File Scanning

**Objective:** Build a complete, classified inventory of every file in the project.

#### 0.2.1 Determine Scan Scope

Identify which directories to scan and which to exclude.

**Must scan:**
- Source directories: `src/`, `lib/`, `app/`, `main/`, `<package>/`
- Test directories: `tests/`, `test/`, `spec/`, `__tests__/`
- Config directories: `config/`, `conf/`
- Script directories: `scripts/`, `bin/`
- Static/asset directories: `static/`, `public/`, `assets/`
- Documentation: `docs/` (only if contains structured docs like OpenAPI specs)
- Root-level config files: `.env.example`, `Dockerfile`, `docker-compose.yml`, `*.config.*`

**Must exclude:**
- `.git/`, `.svn/`, `.hg/`
- `node_modules/`, `vendor/`, `.venv/`, `venv/`
- `dist/`, `build/`, `target/`, `out/`, `.next/`, `.nuxt/`, `.output/`
- `coverage/`, `.nyc_output/`
- `*.log`, `*.lock`, `*.lockb`
- `__pycache__/`, `.mypy_cache/`, `.pytest_cache/`, `.ruff_cache/`
- `.idea/`, `.vscode/` (except if they contain launch configs)
- `framework/`, `plugins/` (the H5 framework directories themselves)

#### 0.2.2 Directory Structure Capture

Capture the full directory tree (excluding paths above) and identify the organizational pattern:

**Organizational pattern detection:**

| Pattern | Signature | Example |
|---------|-----------|---------|
| **Feature-based** | `src/` contains directories like `auth/`, `users/`, `dashboard/`, each with mixed file types | `src/users/components/`, `src/users/services/`, `src/users/models/` |
| **Layer-based** | `src/` contains directories like `components/`, `services/`, `models/`, `utils/` | `src/components/`, `src/services/`, `src/models/` |
| **Hybrid** | `src/` has `shared/` + `features/` where features are feature-based and shared is layer-based | `src/features/users/`, `src/shared/components/` |
| **Flat** | All source files in a single directory (no subdirectories) | `src/index.ts`, `src/App.tsx`, `src/utils.ts` |
| **Empty** | Source directories exist but contain no files (or only placeholder `.gitkeep`) | `src/.gitkeep` |

#### 0.2.3 File Classification

For every source file, assign a classification using the following decision tree (apply in order, first match wins):

```
File at path P:

1. Is P under a test directory OR matches *.{spec,test}.{js,ts,tsx,py,java} OR matches *Test.{java,kt}?
   → type: test

2. Is P in a static/asset directory OR matches image/font/css/scss/less/svg extensions?
   → type: asset

3. Is P under scripts/ or bin/ (and is executable or a .sh/.bat/.ps1 file)?
   → type: script

4. Does P's directory name contain: config/settings/constants/env?
   → type: config

5. Does P's filename contain: middleware/plugin/interceptor/filter/guard?
   → type: middleware

6. Does P's filename contain: controller/route/router/handler?
   → type: controller

7. Does P's filename contain: repository/dao/mapper/datasource?
   → type: repository

8. Does P's filename contain: model/entity/dto/schema/type/interface (definition files only)?
   → type: model

9. Does P's filename contain: util/helper/format/parse/convert?
   → type: utility

10. Is P's filename: main.*, index.*, app.*, server.*, Application.*?
    → type: entry

11. Is P a component file (*.tsx, *.jsx, *.vue, *.svelte) or under a components/ directory?
    → type: component

12. Does P's filename contain: service/manager/provider?
    → type: service

13. Fallback (none of the above matched):
    → type: unknown — flag for manual review
```

For each file, also record:
- File size (lines of code — count non-blank, non-comment lines)
- Whether the file is a barrel export only (`index.*` with only re-exports and no logic)
- Complex files (>200 lines) — flag for potential refactoring

#### 0.2.4 Empty Project Detection

**Check:** After scanning, count all classified source files (excluding test, asset, script, and config types).

- **If count = 0:** Project is empty. Skip Steps 0.3 and 0.4. Go directly to Step 0.5 (minimal docs mode).
- **If count > 0:** Continue to Step 0.3.

Record empty project status in the language stack record.

**Output of Step 0.2:** Complete file inventory with classifications, directory structure pattern, and empty project flag.

### Step 0.3: Identify Module Boundaries

**Objective:** Group source files into cohesive logical modules.

**Skip this step if the project is empty** (proceed directly to Step 0.5 minimal mode).

#### 0.3.1 Module Detection Algorithm

Execute the following algorithm in order. A file can belong to only ONE module. Once assigned, it is removed from the unassigned pool.

**Algorithm:**

```
Unassigned = all non-test, non-asset, non-script source files
Modules = []

// Rule 1: Explicit module markers (strongest signal)
FOR EACH directory D in source tree:
    IF D contains index.{ts,js,jsx,tsx} with export statements:
        Module = { files: all files in D subtree, name: basename(D), type: infer_type(D) }
        ADD Module to Modules
        REMOVE Module.files from Unassigned

// Rule 2: Framework-implied modules
FOR EACH remaining directory D in source tree:
    IF language is Python and D contains __init__.py:
        Module = { files: all .py files in D subtree, name: dotted.path.of.D }
        ADD Module to Modules
    IF language is Java and D corresponds to a package with 3+ .java files:
        Module = { files: all .java files in D, name: package.name.D }
        ADD Module to Modules

// Rule 3: Feature directories
FOR EACH top-level subdirectory D under src/ (or src/features/):
    IF D contains 2+ files AND at least 2 different classification types:
        Module = { files: all files in D subtree, name: basename(D), type: "business" }
        ADD Module to Modules
        REMOVE Module.files from Unassigned

// Rule 4: Layer directories
FOR EACH top-level subdirectory D under src/ that groups by layer:
    Module = { files: all files in D, name: layer_name(D), type: layer_to_module_type(D) }
    ADD Module to Modules
    REMOVE Module.files from Unassigned

// Rule 5: Single-file outlier modules
FOR EACH remaining file F in Unassigned:
    Module = { files: [F], name: stem(F), type: infer_type_from_file(F) }
    ADD Module to Modules
```

#### 0.3.2 Module Type Inference

| Module Name / Path Pattern | Inferred Type |
|---------------------------|---------------|
| Contains `util`, `helper`, `common`, `shared` | `utility` |
| Contains `config`, `settings`, `env`, `constant` | `infrastructure` |
| Contains `db`, `database`, `cache`, `queue`, `messaging`, `log` | `infrastructure` |
| Contains `component`, `ui`, `view`, `page`, `layout` | `ui` |
| Top-level `index` or `main` or `app` | `core` |
| All others | `business` |

### Step 0.4: Analyze Module Dependencies

**Objective:** Map every import/reference relationship between modules.

**Skip this step if the project is empty.**

#### 0.4.1 Dependency Extraction

For every source file in each module, parse import/reference statements:

| Language | Import Pattern | Example |
|----------|---------------|---------|
| TypeScript/JS (ESM) | `import { X } from '...'` | `import { User } from '../models/user'` |
| TypeScript/JS (CJS) | `require('...')` | `const { User } = require('../models/user')` |
| TypeScript/JS (dynamic) | `import('...')` | `const mod = await import('../plugins/renderer')` |
| Java | `import com.xxx.yyy.*` | `import com.example.user.model.User;` |
| Python | `from X import Y` / `import X` | `from ..models.user import User` |

For each import:
1. Resolve the target file path (handle relative imports, path aliases from `tsconfig.json`, Python namespace packages)
2. Determine which module the target file belongs to
3. If the source and target are in different modules, record a dependency edge: `source_module → target_module`

#### 0.4.2 Dependency Classification

For each dependency edge, classify its nature and weight:

| Weight | Criteria | Meaning |
|--------|----------|---------|
| **heavy (3)** | Module A imports from 5+ files in Module B | A is tightly coupled to B |
| **medium (2)** | Module A imports from 2-4 files in Module B | A has significant dependency on B |
| **light (1)** | Module A imports from 1 file in Module B | A has a narrow, specific dependency |
| **dynamic (0)** | Module A uses dynamic/lazy import for Module B | A has a deferred, optional dependency |

Also classify the dependency direction:
- **unidirectional:** A → B only (normal, healthy)
- **bidirectional:** A → B and B → A (potential design issue, flag for review)
- **circular:** A → B → C → A (VIOLATION — must be flagged and reported)

#### 0.4.3 Architecture Rule Validation

Validate each dependency edge against architectural rules:

| Rule | Check | Violation Severity |
|------|-------|-------------------|
| Core → Business | Core modules import from business modules | ERROR |
| Core → UI | Core modules import from UI modules | ERROR |
| Infrastructure → Business | Infrastructure modules import from business modules | ERROR |
| Utility → Any | Utility modules import from any project module | WARNING |
| Circular | Any circular dependency chain | ERROR |

#### 0.4.4 Dependency Matrix

Generate a matrix for the architecture document:

```

           MOD-001  MOD-002  MOD-003  MOD-004  MOD-005  MOD-006  MOD-007  MOD-008
MOD-001      -         -        -        -        -        -        L        -
MOD-002      -         -        H        -        -        -        M        L
MOD-003      -         -        -        -        -        -        L        L
MOD-004      -         -        -        -        -        -        -        L
MOD-005      -         -        -        -        -        -        -        -
MOD-006      -         -        -        -        -        -        -        -
MOD-007      -         -        -        -        -        -        -        -
MOD-008      -         -        -        -        -        -        -        -
(H=Heavy, M=Medium, L=Light, -=None)
```

## Phase 6: Code Review (代码审核)

The Code Review phase is a **mandatory hard gate** between Development Coding and Process Validation. It ensures every line of code is correct, complete, standards-compliant, and free of omissions before validation begins.

### Reviewer: SE Agent
The SE Agent is responsible for code review because they designed the architecture and have full context of the technical requirements.

### Code Review Checklist

The SE Agent MUST verify every item on this checklist. Any FAIL result triggers a challenge against the Dev Agent.

#### CR-1: Requirement Completeness
- [ ] Every functional requirement in `docs/prd.md` (or Dev Story if shortcut path) has a corresponding code implementation
- [ ] Every acceptance criterion in `docs/test-plan.md` is addressed by the implementation
- [ ] No requirement is partially implemented ("TODO", "FIXME", stub code)

**Basis for challenge:** Cite specific PRD requirement ID (FR-XXX) or acceptance criterion (AC-XXX) that is missing or incomplete.

#### CR-2: Dev Story Alignment
- [ ] Every task in `docs/dev-story.md` is implemented
- [ ] File paths in the actual code match those specified in the Dev Story
- [ ] Function signatures, class structures, and interfaces match the Dev Story specifications
- [ ] Deviations from Dev Story (if any) are explicitly documented and justified

**Basis for challenge:** Cite specific Dev Story task ID (TASK-XXX) or implementation detail that is misaligned.

#### CR-3: Standards Compliance
- [ ] Code follows the language-specific coding standards (`framework/standards/coding-standards.<lang>.md`)
- [ ] Naming conventions are consistent (files, variables, functions, classes)
- [ ] File organization follows `framework/standards/project-structure.template.md`
- [ ] No prohibited patterns from the standards "禁止事项" checklist

**Basis for challenge:** Cite specific chapter/section of the coding standards that is violated.

#### CR-4: Architectural Integrity
- [ ] New code does not introduce circular dependencies
- [ ] Module dependency rules are respected (core → business, infra → business forbidden)
- [ ] Public APIs use proper encapsulation (no leaked internal implementation)
- [ ] Changes align with `docs/architecture.md`

**Basis for challenge:** Cite `docs/architecture.md` section or module dependency rule that is violated.

#### CR-5: Correctness
- [ ] All code paths are reachable and logically correct
- [ ] Error handling covers all documented error scenarios
- [ ] Edge cases (null, empty, boundary values) are handled
- [ ] No race conditions or thread-safety issues (where applicable)

**Basis for challenge:** Cite specific error scenario from Dev Story §5 or SE Design §3.1.6 that is unhandled.

#### CR-6: Test Coverage
- [ ] All new functions/methods have corresponding tests
- [ ] Tests follow the Arrange-Act-Assert pattern
- [ ] Test cases cover: happy path, error path, boundary conditions
- [ ] Existing tests pass (no regressions)

**Basis for challenge:** Cite specific function or test case from `docs/test-plan.md` that is missing or failing.

#### CR-7: Security
- [ ] No hardcoded secrets, keys, or credentials
- [ ] All external input is validated at the boundary
- [ ] SQL/command injection vectors are closed (parameterized queries used)
- [ ] No use of `eval()` or equivalent dynamic code execution

**Basis for challenge:** Cite specific security standard from the coding standards §Security section.

#### CR-8: No Omissions
- [ ] No commented-out code blocks (use git history)
- [ ] No empty catch blocks
- [ ] No unreachable code
- [ ] No leftover debug logging or temporary test code
- [ ] All imports are used (no dead imports)

**Basis for challenge:** Cite specific file and line with the omission.

## Execution Protocol

When invoked, the orchestrator MUST execute the following protocol in order:

### 1. Determine Operating Mode

Check initialization state and user intent:
- `docs/.framework-init.lock` does NOT exist → **REJECT lifecycle request**, instruct user to run `@CLAUDE.md 初始化框架`
- Lock file exists + user invokes `@CLAUDE.md 初始化框架` → **Re-initialization** — confirm with user, delete lock, re-run Phase 0
- Lock file age >30 days → **WARN user** that project info may be stale, suggest re-initialization
- Lock file exists + user provides Dev Story → **Entry B (Shortcut)** — execute §Entry B protocol
- Lock file exists + user provides PRD (or invokes default lifecycle) → **Entry A (Full Lifecycle)** — proceed to step 2

### 2. Load Environment

1. Read `docs/architecture.md` to understand the project
2. Load the appropriate coding standards based on project language stack
3. Scan `plugins/` directory for active plugin hooks; build hook registry
4. Verify all framework rule files are accessible

### 3. Pre-Flight Checks

1. **Challenge queue** — check if any challenges are pending from prior phases; if yes, route to the challenged agent for resolution first
2. **Plugin hooks** — check if any `*-pre` hooks exist for the current phase; if yes, execute them in plugin registration order
3. **Standards validation** — confirm the current phase's input artifacts conform to their templates

### 4. Execute Current Phase

1. Load the responsible agent's skill file
2. Provide the agent with: input documents, relevant standards, architecture context
3. Agent produces output following the phase's artifact template
4. Run `*-post` plugin hooks on agent output
5. Validate output against template completeness

### 5. Handoff or Halt

1. Present output to the reviewer agent (or user for phases reviewed by user)
2. If reviewer **accepts** → advance to next phase, go to step 3
3. If reviewer **challenges** → pause lifecycle, route to challenged agent with challenge details
4. If **validation fails** → return to current phase for revision

### 6. Code Review Gate (before Phase 7)

After Phase 5 completes, the orchestrator MUST:
1. Invoke SE Agent in Code Review mode
2. SE Agent executes the 8-item Code Review Checklist (§Phase 6)
3. If APPROVED → advance to Phase 7
4. If CHALLENGED → Dev Agent fixes → re-review → repeat until APPROVED
5. Twice-failed items → escalate to user

### 7. Completion

When Phase 7 passes, report:
- Summary of all phases completed
- Files changed/created
- Test results
- Code Review Report status
- Validation report location

## Challenge Mechanism Summary

The challenge mechanism (详细规则见 `framework/workflows/challenge-mechanism.rule.md`) has **highest priority** in the framework:

1. Any agent can challenge another agent's output by citing a specific standard/clause violation
2. The challenged agent MUST stop current work and resolve the challenge first
3. A valid challenge requires: target, basis (specific standard citation), evidence, impact, and suggested fix
4. Invalid challenges (no cited basis, personal preference) are rejected
5. Escalation to user is available for deadlocked challenges
6. **Code Review challenges are system-generated** — the SE Agent issues them automatically on checklist failures and they follow the same formal challenge rules
